# AI 需求助理 — 产品路线图

> 从 MVP 到正式产品的演进规划
> 基于 QM（需求管理平台）终极愿景

---

## 1. 现状定位

### 1.1 当前状态：MVP ✅

AI 需求助理已经跑通完整链路：

```
一句话需求 → AI 分类 → 逐轮追问 → 结构化 → 归档 → Web 管理端
```

已实现：
- 企业微信消息收发（Agent 统一）
- 3 个 AI Agent（分类/追问/结构化）
- MySQL 持久化 + Redis 会话
- 响应式 Web 管理端（PC + 移动端）
- OAuth 认证（企信内 + 外部浏览器扫码）
- 需求实体 26 个维度字段

### 1.2 终极愿景：QM

> 以需求为轴心的会话式协作平台
> 一需求一群，流程审批全部在 IM 群内完成，平台自动留底、驱动状态机，需求关闭自动散群并归档。

完整设计见：[QM 项目](https://github.com/zyjarge/QM)

## 2. 演进路线

### 🟢 P0 — 产品化基础（1-2 周）

#### 2.1 🔴 代码重构：提取 LlmService

**问题**：`ClassifierAgent`、`QuestionerAgent`、`StructurerAgent` 各写了一遍 LLM 调用（`callLlm()` + `RestTemplate` + 错误处理），代码重复。

**方案**：抽取公共 `LlmService`，统一管理：
- LLM HTTP 调用（超时控制）
- 重试机制（3 次指数退避）
- JSON 响应解析
- 错误处理与 fallback

**工作量**：2 小时

#### 2.2 🔴 前端重写：从单页 HTML 到 React/Vue

**问题**：412 行的单文件 HTML SPA（后扩充到 625 行），JS/CSS/HTML 全耦合，无法支撑后续复杂度。

**方案**：
- 使用 React 18 + TypeScript（与 QM 对齐）
- 或 Vue 3（更轻量）
- 引入 TipTap 富文本编辑器（QM 核心组件）
- 组件化：需求列表、需求详情、审批卡片、状态机面板

**工作量**：2-3 天

**为什么现在就做**：
- 状态机界面、审批卡片、富文本编辑都无法在单文件 HTML 中实现
- 前端是承接 QM 所有能力的界面基础
- 现有前端代码无法增量演进，必须重写

#### 2.3 安全加固

| 事项 | 当前 | 目标 |
|---|---|---|
| LLM API Key | 明文写在 yml | 仅环境变量注入 |
| 企微 Secret | 明文写在 yml | 仅环境变量注入 |
| yml 权限 | 644 | 600 |
| application.yml | 已提交到 git | `.gitignore` 排除，用 `.example` 模板 |

**工作量**：30 分钟

#### 2.4 容器化

**当前**：MySQL 和 Redis 用 docker-compose，应用通过 `nohup java -jar` 直接运行在 mac 上。

**方案**：完善 `docker-compose.yml`，将 Spring Boot 也容器化：

```yaml
services:
  app:
    build: .
    ports:
      - "9080:9080"
    environment:
      - MYSQL_PASSWORD=${MYSQL_PASSWORD}
      - LLM_API_KEY=${LLM_API_KEY}
      - WECOM_SECRET=${WECOM_SECRET}
    depends_on:
      - mysql
      - redis
```

**工作量**：半天

**好处**：
- 环境一致，消除"在我机器上能跑"
- 便于部署到阿里云 ECS
- 与 QM 的 Docker Compose 策略一致

#### 2.5 LLM 调用可靠性

| 改进 | 当前 | 目标 |
|---|---|---|
| 超时控制 | 无（可能挂死） | 30 秒超时 |
| 重试机制 | 无 | 3 次指数退避 |
| 熔断 | 无 | 连续失败后降级 |
| Token 限制 | 硬编码 200/500 | 按 Agent 配置 |

**工作量**：半天

### 🟡 P1 — 核心能力扩展（2-4 周）

#### 3.1 需求状态机

**当前**：5 个静态状态（SUBMITTED / QUESTIONING / IN_PROGRESS / ARCHIVED / DONE），通过 PATCH API 手动切换。

**目标**：引入状态机引擎

```
SUBMITTED → 评审中 → 基线签认 → 开发中 → 验收中 → 已验收 → DONE
                                                                 ↓
                                                              已归档
```

参考 QM 的 12 态状态机设计（`docs/02-state-machine.md`），P1 阶段先实现 6-8 态简化版。

**关键能力**：
- 状态流转规则引擎
- 状态变更回调（触发通知）
- 权限校验（谁可以执行哪些操作）
- 状态变更审计

#### 3.2 群内审批卡片

**当前**：用户在企信里发消息聊天，AI 回复。

**目标**：在企信群内发送交互式审批卡片

```
┌──────────────────────────────┐
│ 📋 需求评审 #1024            │
│                              │
│ 标题：销售月报自动化          │
│ 提交人：张三                  │
│ 优先级：P1                   │
│                              │
│  [通过]  [驳回]  [修改意见]   │
└──────────────────────────────┘
```

**依赖**：前端重写（审批卡片组件）

#### 3.3 通知体系

**当前**：仅 AI 回复消息。

**目标**：状态变更时主动通知相关干系人

| 事件 | 通知对象 | 渠道 |
|---|---|---|
| 新需求提交 | 产品经理 | 企信消息 |
| 状态变更 | 提交人 + 指派人 | 企信消息 |
| 评审通过/驳回 | 提交人 | 企信消息 |
| 临近截止日期 | 指派人 | 企信消息 |

#### 3.4 全文搜索

**当前**：SQL `LIKE %keyword%` 搜索标题和原始内容，不支持模糊匹配和相关性排序。

**目标**：引入 Meilisearch（QM 已实现）

- 全字段搜索（标题、背景、验收标准、问答历史）
- 相关性排序
- 搜索结果高亮
- 后续可扩展为语义搜索（pgvector）

#### 3.5 数据库迁移：MySQL → PostgreSQL

**当前**：MySQL 8 + JPA。

**目标**：PostgreSQL 16 + pgvector（与 QM 对齐）

**原因**：
- pgvector 支持向量搜索（为后续语义搜索铺路）
- PostgreSQL 的 JSON/全文搜索能力更强
- QM 设计全面基于 PostgreSQL

**策略**：
- P0 阶段保持 MySQL，不影响业务
- P1 评估迁移成本和工具
- 使用 flyway 管理 DDL，确保可回滚

### 🟠 P2 — 产品化完善（1-2 月）

#### 4.1 富文本编辑器

**当前**：纯文本输入。

**目标**：TipTap 富文本编辑器（QM 核心组件）

- 支持排版、图片、表格
- 需求描述更丰富
- 验收标准更清晰

#### 4.2 文件附件（MinIO）

**当前**：无文件上传支持。

**目标**：对接 MinIO 对象存储（QM 已规划）

- 上传原型图、设计稿
- 上传附件文档
- 附件预览

#### 4.3 变更管理 + 版本追踪

**当前**：简单审计日志（字段变更记录）。

**目标**：
- 需求版本管理（每次变更加版号）
- 内容指纹（SHA256，防篡改）
- 版本对比（diff）

#### 4.4 多 IM 支持

**当前**：仅企业微信。

**目标**：预留 IM 抽象层

```java
interface ImClient {
    void sendMessage(ImMessage msg);
    void sendCard(ImCard card);
    void createGroup(ImGroup group);
    void disbandGroup(String groupId);
}
```

P2 先对齐 QM 的飞书支持，再做 IM 抽象。

#### 4.5 监控告警

| 组件 | 工具 |
|---|---|
| 应用指标 | Spring Boot Actuator + Micrometer |
| 指标收集 | Prometheus |
| 可视化 | Grafana |
| 告警 | AlertManager |
| 日志聚合 | 文件 → 后续 ELK/Loki |

## 5. 长期愿景：与 QM 对齐

### 5.1 QM 的核心设计理念

```
业务方提需求(群对话/表单)
  → 自动建群,干系人全部就位
  → AI/模板引导澄清补全
  → 群内卡片评审(会签)
  → 业务负责人群内一键基线签认(内容指纹锁定)
  → 开发/验收(状态播报在群)
  → 归档:导出全部群记录 → 解散群
  → 需求库全文/语义可检索,全链路可追溯
```

### 5.2 当前项目与 QM 的差距

| 维度 | 当前项目 | QM 目标 | 对齐策略 |
|---|---|---|---|
| IM 平台 | 企微 Only | 飞书 → 多 IM | P2 做 IM 抽象 |
| 群协作 | 无 | 一需求一群 | P1 做群引擎 |
| 审批流程 | 无 | 群内卡片会签 | P1 做审批卡片 |
| 状态机 | 5 态手动 | 12 态自动驱动 | P1 引入状态机 |
| 搜索 | SQL LIKE | Meilisearch + pgvector | P1 引入 Meilisearch |
| 编辑器 | 纯文本 | TipTap 富文本 | P0 前端重写时引入 |
| 文件 | 无 | MinIO 对象存储 | P2 对接 |
| 数据库 | MySQL | PostgreSQL + pgvector | P1 评估迁移 |
| 前端 | 单页 HTML | React 18 + TypeScript | P0 重写 |

### 5.3 代码库策略

**建议：当前项目作为 QM 的 WeCom 先行版**

- **不合并代码库**，当前项目独立演进
- 当前项目的职责：**快速迭代验证企微场景**
- QM 代码库：**承载完整产品设计**
- 两个项目积累的经验最终汇聚到统一架构
- 当当前项目的功能覆盖率达到 QM 的 80% 以上时，考虑合并
